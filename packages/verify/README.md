# Sentence verifier (P12)

Private, offline-tested implementation. **Not live accepted, persisted, or wired into the web service.** P9's existing endpoint continues returning `verification_status: "pending"`. No public flag changes, deployment, database operation, credentials retrieval or provider call were made. Keep `PUBLIC_SITE=off`.

`verifyInvestigation(pendingResult, dependencies)` accepts the P9 result structure and returns `{result, audit, removed_claim_ids}`. The input is unchanged. The separate output type has `verification_status: "verified" | "partial" | "failed"`; `status` remains P9's lifecycle value (`completed`). Verified means every retained sentence passed; partial also reports removed sentences; failed has no answer. All retained claims have `verdict: "supported"`. The summary and card references are rebuilt from retained or fully rechecked replacements. Writer-supplied sources and verdicts do not establish support. Filing metadata is rebuilt from fresh source rows. Vote-only evidence legitimately has no filing ID; do not fabricate one.

The output is a server computation, not an authorization credential. Never accept a browser-submitted verified envelope or update public/export state from a string flag. The host must separately authorize the user, own the saved investigation/session, persist the outcome, invalidate it after claim edits, and apply the product's human publication approval gate. Neither `status="verified"` nor a previously recorded writer verdict is a P12 persistence signal. Aggregate cost and tokens are null because combined writer, repair, tool and verifier billing has not been reconciled.

## Checks, in order

1. Bind exact visible sentence text to its recorded claim. Load all cited money/lobby/vote/interest rows with generated `SELECT`s through the existing `packages/tools` MCP server. Match the entire edge and filing UUID sets; reject missing, duplicate, changed or truncated rows and absent filing URLs. Votes have no filing row in the existing schema.
2. Recompute every digit-based number via a bounded proposal (`VerificationPlan`). UTF-16 spans bind every visible numeric token exactly once. The plan supplies an operation and existing cited IDs, never SQL, expected totals, tables or expressions. Amount sums and row counts execute fresh fixed SQL over those IDs; exact decimal strings are checked again with `bigint`. Numeric/date fields must equal their source field. Roll-call numbers use the complete `vote_base_rate` tool and a cited bill UUID plus exact date/location/motion. Written-out numeric phrases and unsupported formats fail closed and can be rewritten with digits. This version does not support arbitrary derived financial ratios or summing Form 700 value ranges.
3. Check supplied name spans against party-name fields and load entity attributes via `v_entities`. Pairs marked `likely_same_donor`, or claims marked likely, must say “likely the same donor.” A likely identity cannot be used in `sum_amount` donor totals. Directly reporting an exact filing amount remains possible with the field operation and qualified wording. Separate entity IDs remain separate; the verifier never merges them.
4. Ask an independent family model to label the sentence `supported`, `overstated`, or `unsupported`. It receives only the sentence and newly loaded rows (including entity metadata and all-member rows used for recomputation). No writer messages, question, scratchpad, tools, plans or repair history are included. Missing configuration, unavailable/unfinished/malformed responses and an unconfirmed returned model ID fail closed. No provider fallback exists.
5. A money/vote comparison must contain the verified aye count and all-member denominator for **every cited exact roll call**, explicitly labeled as all members. No contributor subgroup filter is accepted. Duplicate members, inconsistent counts, cited-member mismatches and truncated base rates fail closed. Counts include ayes, noes and non-voting records; they describe the recorded roll call, not an assumption about constitutional chamber size.
6. Reject the neutral-language phrases listed in AGENTS.md, with Unicode normalization.

The independent model checks whether selected computations/rows actually support the meaning of the sentence; matching a number elsewhere in a filing is insufficient support. The plan and any caller-provided stub judge are untrusted/trusted test boundaries respectively: production must construct its judge using the configured TokenRouter adapter. No output from the offline stub is live verification evidence.

## Host integration

Use the exported `createReadTools(authenticatedPackagesToolsMcpCaller)`. The adapter exposes only `query` and `vote_base_rate`, unwraps the server's text result, and has no database client, database credentials, or write-tool path. The existing tools server owns the read-only transaction, role grants, query wrapping, timeout and row limit. Keep caller authentication inside the server.

Construct the independent judge with `createTokenRouterJudge(tokenRouterConfiguration(serverEnvironment))`. There is no default verifier model. The deployment owner must confirm the exact account-supported model ID, its family and the actual configured HarnessRouter writer model/family. Known provider prefixes have conservative family mappings; unknown families are unavailable until reviewed. The writer and verifier must have different families. The three readiness flags in `.env.example` attest reviewed host, account catalog and live provider routing; do not set them from model output. Model aliases or missing model identity fail closed until their exact provider response contract is reviewed.

The fixed sponsor endpoint is `https://api.tokenrouter.com/v1/chat/completions`, using Chat Completions as documented by the intended PaleBlueDot TokenRouter. Redirects are refused. Do not substitute similarly named services. Do not retrieve or use deployment credentials until the owner confirms the provider host and secure configuration.

A `Session` requires the saved `investigation_id`, `response_id`, **`session_id`**, and `harness_id`. `createHarnessRepair(ownedContinuationTransport, loadRecordedClaim)` constructs a continuation with `previous_response_id` and the same session/harness. It reloads the revised claim through the host's existing narrow investigation-owned server store; a writer-supplied claim object never establishes citation existence. Each new response ID is chained to the preceding response while session, harness and investigation remain unchanged. Verification reruns from the first check. Each original sentence gets at most two repair attempts; remaining failures are removed from sentences, summary, card and output claims. Failure reasons are returned to that session as JSON data. No callback means immediate removal after a failed check. No new-session fallback exists.

P9 currently saves a response ID but has no persisted session-ID mapping or number-plan output. The host must retrieve/own `response.metadata.session_id`, supply plans, wire continuation transport and reload actual owned claim rows before enabling this package. HarnessRouter's general quickstart shows `/v1/responses` with `metadata.harness_id`, whereas the detailed continuation page shows `/{harness_id}/v1/responses`. This package deliberately leaves HTTP transport to the host's confirmed deployed `/v1/uhp` contract rather than sending a key to speculative endpoints. Missing setup is a release blocker.

## Evidence and validation

`fixtures.json` contains exactly 30 explicitly false/disallowed negative examples beside their actual source-derived originals: ten wrong amounts, six names deliberately substituted with different real public-record names, six incorrect all-member denominators, and all eight banned phrases. The copied financial edge/entity/filing UUIDs are actual committed CAL-ACCESS slice identifiers. Legislative source bill IDs/counts/names come from the committed official vote-page fixture; absent database UUIDs are never claimed as real. Tests create ephemeral in-memory IDs only for adapter/session/claim infrastructure. No financial party–legislator relationship is asserted. Regenerate without network/database access with `python3 packages/verify/test/make-fixtures.py`.

Run `bun test packages/verify/test` and `bun run --filter @aletheia/verify typecheck`. Tests cover binding, exact amounts, source hydration, ordered rejection, all-member completeness, malformed/unavailable providers, missing/different family config, fixed sponsor host, immutable pending results, filtered cards/summary, same-session chaining, persisted-claim reload and retry exhaustion. All provider/tool calls in these tests are offline stubs. **No live SQL, HarnessRouter continuation, TokenRouter verdict, end-to-end investigation or deployment is claimed.** TypeScript and Bun types reuse the repository's existing locked development packages; no new library/version was added.
