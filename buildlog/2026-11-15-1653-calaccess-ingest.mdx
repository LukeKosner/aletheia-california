## Shipped

- `uv run python -m ingest.calaccess`: one command that downloads, stages, transforms and loads CAL-ACCESS into Postgres (`py/ingest/src/ingest/calaccess/`). Full history by default; `--since YYYY-MM-DD` limits the window, and `--no-db` stops before Postgres.
- Download: `dbwebexport.zip` saved unchanged to `data/raw/calaccess/2026-11-15/`, with URL, time, SHA-256, size, Last-Modified and ETag in `data/raw/MANIFEST.csv`. Reruns skip the download when the state's ETag hasn't changed.
- Staging: 18 tables streamed from the zip into DuckDB as text. The export is never unzipped to disk. Rows split by embedded line breaks are rejoined. Every unplaceable row goes to `_rejects` with its raw text and per-table counts go to `_load_log`; the run stops if any physical line is unaccounted for.
- Transform: latest amendment only. One entity per filer keyed `calaccess:filer:<FILER_ID>` (legacy ids mapped through `FILER_XREF_CD`, never by name). One temporary entity plus `entity_alias` per distinct raw donor/payee/lender/client/IE target. Filing rows carry the public PDF URL. Money edges carry schedule and line. Lobbying rows carry bill numbers extracted from activity text and text memos. `out_exclusions` counts every itemized row that did not become an edge, with the reason.
- Load: one Postgres transaction with deterministic ids and upserts. Older amendments' filings and edges are deleted when a newer amendment arrives.
- Tests: 6 unit tests on real export lines (no data needed, run in CI), and the Power Search totals test (skips without data or a database).

## Broke or learned

- Power Search's committee total = Form 460 Schedule A + Schedule C + Form 497 late contributions dated after the committee's last 460 period + the 460's unitemized lump sums. The remaining gaps are exactly those unitemized sums ($47,120.27 Mahan, $32,679.47 Steyer); they live on the 460 summary page, not in itemized rows.
- 497 late contributions are usually itemized again on the next 460. Both sets are in money_edge (schedules `F497P1` and `A`), so sums across schedules double count. The totals test shows the filter that avoids it.
- Disk: the export is 10.6 GB unzipped and staging plus transform peaks around 10 GB. This shared Mac ran out of disk mid-run; streaming from the zip and deduping raw parties as they are inserted brought the footprint down.
- A full-history load is roughly 12–16 GB in Postgres. That is more than the Neon free plan holds, so the dev database needs the Launch plan (estimated $2.50–4 for a week) before a full load. Not run against Neon: agents don't write to the project database.
- DuckDB 2.0 rejects `x -> expr` lambdas (use `lambda x: expr`). A macro argument named like a column inside the macro's subquery is silently captured by that column, so the filer-xref lookup columns are prefixed `xr_`.
- `MEMO_CODE` is blank on most rows, so `memo_code = 'X'` is NULL, not false. Without `coalesce` it filtered out 99.99% of edges on the first run.
- Old lobbying filer ids (`L25430`, `E24542`) map to current ids through FILER_XREF_CD (3,618 of 3,630 found).
- TEXT_MEMO_CD splits long text across lines and tabs; it is parsed with "last column is free text" rules (5,802 memos rejoined, 0 rejected).
- Filing URLs (`pdfgen.prg?filingid=…&amendid=…`) could not be opened here: the state's bot check serves an empty page to automated clients. Unverified in this session.
